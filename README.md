
# Отчёт по проекту

## Финальный конфиг

Модель: Qwen/Qwen2.5-1.5B-Instruct
Параметры vLLM / генерации: temperature=0.3, top_p=0.9, top_k=20, repetition_penalty=1.1, max_tokens=350, concurrency=16.
Количество повторов при браке: Установлено MAX_ATTEMPTS = 3. Если модель возвращает невалидный JSON или нарушает правила длины/полей, 
используется механизм самоисправления (self-correction): отправляется её же ответ и текст ошибки обратно в историю диалога 
с указанием исправить конкретную ошибку. Трех попыток хватает, чтобы исправить почти все случайные сбои.

Итоговый выбранный набор параметров:
temperature: 0.3,
top_p: 0.9,
top_k: 20,
repetition_penalty: 1.1,
max_tokens: 350

top_k = 20: 
Ограничение выбора 20 наиболее вероятными токенами показало лучший результат. Отсечение «хвоста» распределения полностью исключает генерацию невалидного синтаксиса и критических ошибок структуры JSON.

temperature = 0.3:
Умеренное значение 0.3 обеспечивает максимальную надежность (0.9–1.0 в зависимости от топ-к). Полностью детерминированный режим (temperature = 0.0) снижает показатель до 0.8 из-за зацикливания модели на однотипных шаблонах, а более высокая температура (0.7) дает стабильные 0.9, но увеличивает разброс генерации.

top_p = 0.9 (Контроль расхода токенов):
Сужение ядра вероятностей до 0.9 помогает модели удерживать высокую точность. Снятие ограничения до 1.0 сохраняет валидность на уровне 0.9, но приводит к заметному раздуванию средней длины описания (367.9 символов) и перерасходу токенов (360.7).

repetition_penalty = 1.1 (Борьба с тавтологией):
Стандартный штраф 1.1 оптимален для связного текста. Полное отсутствие штрафа (1.0) проваливает валидность до минимума (0.7) из-за бесконечных повторов в списках и описании. Слишком агрессивный штраф (1.2) снижает показатель до 0.85, заставляя модель искусственно усложнять структуру.

max_tokens = 350 (Защита от синтаксических обрывов):
Слишком жесткий лимит в 250 токенов снижает валидность до 0.8 из-за обрывов JSON на середине, в то время как избыточный запас в 500 токенов не дает прироста точности (valid_rate: 0.85), избыточно расходуя контекст.


## Сравнение с моделью через API. Стоимость и решение

В начале проекта планировалось запускать эксперимент через OpenRouter (с использованием бесплатных моделей и динамического подбора под JSON mode). 
Однако в процессе возникли некоторые проблемы, такие как: жесткие лимиты и ошибки 429 (Rate Limit),
так как бесплатные пулы моделей на OpenRouter перегружены. Из-за этого скрипт постоянно падал по таймаутам и ограничениям по частоте запросов, 
даже несмотря на попытки ставить паузы.
Кроме того, модели в открытом доступе часто уходили в оффлайн (сервер у провайдера мог неожиданно упасть, выдать ошибку 503 Service Unavailable 
или модель вообще временно исчезала из доступа), меняли поведение или не справлялись со строгой JSON-валидацией, портя чистоту эксперимента.
Из-за такой нестабильности я полностью отказалась от OpenRouter и использовала прямой API DeepSeek, 
у которого предсказуемые лимиты и стабильная работа.

| Что сравниваем                            | Локальная модель (vLLM, Qwen2.5-1.5B) | Модель через API (DeepSeek-Chat) |
| :---------------------------------------: | :-----------------------------------: | :------------------------------: |
| **Доля валидных карточек (Качество)**     | 93.3% (280/300)                       | 100.0% (20/20)                   |
| **Входных токенов на 1 карточку**         | ~1,019 токенов                        | ~1,332 токенов                   |
| **Выходных токенов на 1 карточку**        | ~311 токенов                          | ~221 токенов                     |
| **Среднее время на 1 карточку (Latency)** | ~9.4 сек                              | ~2.4 сек                         |
| **Стоимость 1000 карточек**               | 19.9                                  | 39.9                             |

Модель через DeepSeek API показала безупречное качество (100% валидных карточек с первой попытки), так как коммерческие модели лучше следуют сложным JSON-инструкциям. 
Локальная модель Qwen2.5-1.5B набрала 93.3%, но часть брака возникала из-за ограничений по длине предложений (description).
DeepSeek тратит больше входных токенов (~1,332 против ~1,019 у Qwen), потому что разный токенайзер. При этом на генерацию ответа (выходные токены) DeepSeek тратит меньше за счет большей лаконичности (~221 против ~311).
По времени на один запрос API отдает ответ быстрее (~2.4 сек), но общая пропускная способность при пакетной обработке на локальной vLLM достигается за счет эффективного continuous batching.

Расчёт стоимости обоими способами (с условными ценами):
1. Свой сервер на ВМ (T4, аренда 65 рублей/час): Полный прогон 300 карточек занял 331.3 секунды (~0.092 часа).
(331.3 / 3600 * 65) / 300 * 1000 = 19.9 рублей за 1000 карточек. Это укладывается в целевой порог (не выше 25 рублей).

2. Через внешний API (DeepSeek-Chat):
По реальным токенам из прогона (26,633 входных и 4,422 выходных на 20 товаров):
(26633 * 20 + 4422 * 60) / 1 000 000 / 20 * 1000 = 39.9 рублей за 1000 карточек.

Аренда виртуальной машины с GPU оплачивается по часам независимо от того, идет в данный момент расчет или GPU простаивает.
Если каталог обновляется регулярно и большими пачками, собственный сервер на vLLM загружен работой, и его себестоимость минимальна (19.9 рублей / 1000 карточек).
Если генерация карточек запускается редко или маленькими партиями, затраты на аренду простаивающей ВМ в течение месяца превысят стоимость токенов. В таком случае внешний API становится выгоднее, так как вы платите ровно за то количество токенов, которое использовали, без переплаты за аренду сервера.


## Замеры

| Уровень параллелизма (`concurrency`) | Время выполнения (`elapsed_sec`) | Пропускная способность (`throughput`, тов/сек) |
| :----------------------------------: | :------------------------------: | :--------------------------------------------: |
|                  1                   |        281.26 с (~4.7 мин)       |                      0.11                      |
|                  4                   |         89.86 с (~1.5 мин)       |                      0.33                      |
|                  16                  |         52.49 с (~52 сек)        |                      0.57                      |
|                  32                  |         43.42 с (~43 сек)        |                      0.69                      |

С увеличением числа concurrency время обработки 30 товаров сокращается в разы (с 281 секунды при одиночных запросах до 43 секунд при 32 параллельных потоках). Это наглядно демонстрирует работу непрерывного батчинга (continuous batching) на стороне сервера vLLM - GPU эффективно обрабатывает несколько запросов одновременно, а не простаивает в ожидании каждого по очереди.
При переходе от concurrency = 1 к 4 скорость вырастает в 3 раза. При переходе от 4 к 16 скорость вырастает еще почти в 1.7 раза.
Если поднять параллелизм с 16 до 32, скорость почти не вырастет (всего на 21%): у нас в тесте всего 30 товаров, поэтому больше за раз всё равно не обработаешь - система упирается в потолок. Но смысла в этом увеличении особо нет: общая пачка быстрее не обработается, а вот ждать ответа по конкретным запросам придётся дольше из-за очереди.
Следовательно, уровень concurrency = 16 является рабочей точкой. На нём достигается высокая пропускная способность, а сервер ещё не перегружается избыточными очередями.


## Длинный вход

Перед отправкой мы считаю токены через токенайзер. Если текст товара превышает 1500 токенов или у товара слишком много отзывов (>20), 
данные не отбрасываются, а сжимаются с помощью короткого вспомогательного запроса к модели. 
Отзывы превращаются в компактное резюме на 2–3 предложения с главными плюсами и минусами, что спасает от переполнения контекста.
